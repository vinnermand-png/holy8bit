# HOLY8BIT Supabase Infrastructure

This directory contains the database migration and structural Bible reference seed for the separate HOLY8BIT development Supabase project.

## Source data

- Book/chapter structure: `https://free.bible/bible/books.json`
- Verse-coordinate reference: `https://free.bible/bible/web/{book}/{chapter}.json`
- Edition: Free.Bible WEB coordinate data
- No Scripture text is imported by the reference seed.

`supabase/seed/bible-reference.sql` is generated by `npm run generate:bible-seed`. The generator validates 66 books and produces 1,189 chapter rows using the source chapter JSON. Regenerate it only when the pinned source data is intentionally reviewed.

## Local setup

1. Install the Supabase CLI.
2. Create or select the HOLY8BIT development project.
3. Set `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, and the server-only `SUPABASE_SECRET_KEY` in `.env.local`.
4. Authenticate the Supabase CLI with a Supabase Management access token. The project API keys are not CLI access tokens.
5. Link the CLI to the development project by project ref.
6. Apply migrations with `supabase db push`.
7. Apply the structural seed through the approved development workflow.

## First published work

Migrations and seed create structure only; they never create content. Once they are applied:

1. create the first administrator: add a user in Supabase Auth, then insert that user's id into `admin_users` (`role = 'owner'`, `is_active = true`),
2. sign in at `/admin` and publish a Scripture Work - the studio provisions the passage through `ensure_bible_passage`, uploads the artwork to `scripture-media`, and can publish immediately,
3. attach wallpaper renditions from the studio if the artwork should be downloadable (`wallpaper-media`),
4. the work then appears in `/scripture`, its book page, its passage page, `/scripture/journey`, and `/wallpapers` without touching any page code.

A passage page stays 404 until a published work exists for it. That is correct behaviour, not a missing route.

The studio reports the publishing source state in its SYSTEM block, so an unapplied migration, a missing environment variable, and an unreachable project are visible in the product instead of only in the build logs.

Production must use a separate Supabase project and must never be targeted by local destructive commands.

## Security

The publishable key is safe for browser clients under RLS. `SUPABASE_SECRET_KEY` is server-only, bypasses normal RLS protections, and must never be imported into a Client Component or committed to Git.

The four private Storage buckets are created by the core migration:

- `scripture-media`
- `scripture-covers`
- `film-media`
- `film-covers`

Public media delivery should use server-generated signed URLs for published records.

## Scripture text

The reference seed contains structure and verse coordinates only. It does not import WEB/WEBU Scripture text. A separate translation decision and license verification are required before adding Bible text tables or publishing full passage text.

The public app already ships the READ contract for this decision in `lib/bible/text.ts`. `configureScriptureTextProvider()` registers a licensed translation and `getScriptureText()` reports an explicit `translation-not-configured` state until then, so no Scripture text is hardcoded into components or duplicated per Scripture Work.

Book slugs in the seed are derived from the canonical display name and match the public route segments (for example `/scripture/song-of-songs`). Regenerate the seed with `npm run generate:bible-seed` rather than editing slugs by hand.
